# 详细方案

## 桌面小组件（0.31.0，阻塞：需设备）

**结论：可行，而且数据层几乎不用改。** `ScheduleService` 全是纯函数
（`planForToday` / `weekEntries` / `totalSections`），widget 只要能从磁盘读出
课表快照 + 作息 + 设置，就能自己算出"下一节课"，不需要 ViewModel。

### 先确认现状

| 项 | 值 | 对 widget 的影响 |
|---|---|---|
| Kotlin / Compose 编译器 | 1.9.24 / **1.5.14** | Glance 1.1.1 官方示例要求 1.5.15，差一个 patch；大概率能直接编，若报 ABI 错就升 Kotlin 1.9.25 |
| minSdk | 24 | Glance 要求 21+，够 |
| R8 | preview/release 已开 | Glance 自带 consumer rules，另需 `-keep` 住 receiver |
| 现有 appwidget 配置 | **无** | 从零加 |
| `AppContainer` | MainActivity 里 `new` | **widget 拿不到**，需要进程级单例 |

### 三个方案

| | A. Glance 1.1.1（推荐） | B. RemoteViews + XML | C. 不做组件 |
|---|---|---|---|
| 体积 | +300~500KB（2.1 → ~2.5MB） | +0（无新依赖） | 0 |
| UI 能力 | Compose 语法、RemoteViews 现实：无 Canvas / 无模糊 | 最低，只能拼 TextView/ImageView | —— |
| 代码量 | 小（一个 Composable 一张卡） | 大（XML + 手写 update 逻辑） | 0 |
| 兼容性 | minSdk 21+，`cornerRadius` 仅 31+ | 全版本一致 | —— |

选 A。B 的唯一优势是体积，而 400KB 对 2MB 的包不构成理由。

### 形态：三个尺寸，共用一套行式语言（10-28 定稿）

统一为「起止时间列 + 竖色条 + 课名/教室 + 右对齐节次·教师」，一个
`WidgetRow(wide: Boolean)` 出两个宽度。

| 尺寸 | 内容 | 行高 | 一屏可见 | 滚动 |
|---|---|---|---|---|
| 2×2 | 只放下一节：大号时间 / 课名 / 教室 / 倒计时胶囊 | — | 1 | 否 |
| 4×2 | 双行版，超出一门上滑 | 45 | 3 | **是**（`LazyColumn`） |
| 2×4 | 双行版，超出四门上滑；底部固定周进度条 | 58 | 4 | **是**（`LazyColumn`） |

两个列表尺寸共用同一套 `LazyColumn` 骨架，只有行高和可见行数不同，
所以「滚动」这件事只有一条实现路径，不存在 4×2 能滚而 2×4 不能的错位。

**首行恒为下一节课**：渲染前剔除「结束时间早于当前」的条目，4×2 把已上课时折叠进标题栏
（`周三 · 第 6 周` + `已上 2 节 · 还有 4 节`），2×4 折叠进底部周进度那一行。
这是唯一可靠的自动对齐 —— Glance 没有 `scrollTo(index)`，靠数据裁剪比靠滚动定位稳，
且 <12 不会因刷新跳回顶部。

### 落点

- [ ] `app/build.gradle.kts`：`androidx.glance:glance-appwidget:1.1.1`
      + `androidx.glance:glance-material3:1.1.1`
- [ ] `NbuLiteApp.kt`：`AppContainer` 加进程级单例 `AppContainer.get(context)`
      —— 现在 `MainActivity` 里 new 的实例 widget 根本拿不到，而 widget 每次刷新都新建
      一个 Room + DataStore 连接是浪费
- [ ] `widget/NextClassWidget.kt`（`GlanceAppWidget`）+ `NextClassReceiver`（`GlanceAppWidgetReceiver`）
- [ ] `widget/WidgetRow.kt`：`WidgetRow(wide: Boolean)` —— `wide=true` 给 4×2
      （318dp 宽、行高 45、右侧多一节次/教师列），`false` 给 2×4（138dp 宽、行高 58、
      教室在课名下）。列宽全部硬固定（时间列 44 / 色条 +12 / 课名弹性 / 右列右对齐 34），
      **禁用 `defaultWeight` 混排** —— 滚动列表每行独立 inflate，只要有一列自适应就会行间错位
- [ ] `widget/TodayListWidget.kt`：4×2 与 2×4 共用同一个 `LazyColumn`，
      只有行高与可见行数不同；2×4 的周进度条固定在列表外（`Column` 底部），不参与滚动
- [ ] `itemId = courseId * 100 + 当日序号`：两张列表都要给，不稳定 itemId 会让每次
      update 回到顶部
- [ ] `ScheduleService.kt` 加 `remainingToday(now)`：剔除已结束条目，
      返回 `(已上课时数, 剩余列表)`，widget 与 2×2 共用
- [ ] `res/xml/*_widget_info.xml`（每尺寸一份）：`targetCellWidth/Height`（31+）、
      `minWidth = 70n - 30`（旧版）、`resizeMode="horizontal|vertical"`、
      `updatePeriodMillis = 1800000`、`widgetCategory="home_screen"`；
      `SizeMode.Responsive` 给 (110,110)/(110,220)/(250,110)/(250,220) 四档预生成
- [ ] `AndroidManifest.xml`：注册 receiver + `android.appwidget.action.APPWIDGET_UPDATE`
- [ ] `widget/WidgetTheme.kt`：把 `SeedColor` + 深浅换算成 `GlanceTheme` 的 ColorProviders
      —— **应用主题是运行时 seed，widget 用不了 `MaterialTheme`，必须自己读 DataStore 重建**

### 刷新：这是最容易做错的一处

widget 跑在 launcher 进程，**没有 ViewModel、没有 Compose 状态**，
只能在 `provideGlance` 里 suspend 取一次数，然后一次性渲染。三条触发源：

- [ ] 数据变更：`TimetableRepository` 写入后调 `NextClassWidget().updateAll(context)`
- [ ] 上下课边界：复用 `ClassReminderScheduler` 已有的下课撤销闹钟，在 receiver 里顺带刷一次
- [ ] 兜底：`updatePeriodMillis = 30min`（系统下限）
- [ ] **不要在每分钟的倒计时里 `update()`**：4×2 与 2×4 都是 `LazyColumn`，整表重建会打断
      滚动并把位置弹回顶部。倒计时只在 2×2 那张卡上做，且随「下一节切换」一起刷
- **不能依赖内存缓存**：进程被杀后 widget 仍要能画出来，所以只能读磁盘

### 必须提前承认的限制

- **亚克力做不到**。RemoteViews 没有模糊、噪点、渐变描边，widget 只能是纯色 + 圆角。
  侧栏那套 `acrylicPanel` 一点都用不上。
- `cornerRadius` 仅 API 31+，24–30 得退回 shape drawable。
- 无 Canvas、无自定义绘制、无动画 —— widget 是"每次更新重画一张静态图"。
- 自定义字体在 Glance 里支持有限，**内嵌的 Noto Serif 子集可能用不上**，需实测；
  不行就退回系统 sans（数字会跟应用内不一致，可接受）。
- `LazyColumn` 会被翻译成真正的 `ListView`（RemoteViews collection），因此：
  行高必须写死、滚动位置只在 **Android 12+ 且提供稳定 `itemId`** 时保留，
  12 以下每次 update 回到顶部；部分第三方桌面/老 ROM 直接不支持集合滚动，列表会被裁切
- 「现在」那条时间指示线做不了：列表内元素跟着内容滚，RemoteViews 没有 z 轴叠放
- `Text` 不支持 `fontFeatureSettings`，等不了宽数字，时间列只能靠固定宽度兜底
- 列表有 item 上限，`LazyColumn` 在 <31 上走另一条路径。

### 风险

- 体积 2.1 → ~2.5MB，可接受（jsDelivr 单文件限制 20MB，离得远）
- R8 目前只在 preview/release 开，debug 不混淆 —— widget 只在正式包上验一次才准
- 各 launcher 脾气不同：MIUI / ColorOS 对圆角裁剪、尺寸吸附、刷新频率都有额外处理
- 首次添加时 `provideGlance` 可能还没数据，要用 `glance_default_loading_layout` 占位

### 排期与前置

- 排在 **0.31.0**，前置是 0.30.0 验收完 —— widget 要读 `showFullTimetable`（行数/列数）
  和主题色，这两样都在 0.30.0 定型
- 按 **2×2 → 4×2 → 2×4** 的顺序出，每张单独可装可验：
  2×2 是"能不能做"的最小切片（不带列表、固定浅色底），4×2 才引入 `LazyColumn` 与行式布局，
  2×4 复用同一个骨架、只换行高与宽度，基本是白送
- 若滚动在真机上体验崩（跳回顶部 / 部分桌面不支持集合滚动），**两张列表一起降级**：
  4×2 回「行高 29 单行、一屏 4 门、不滚动」，2×4 回「固定 4 行 + 底部『还有 N 节』」。
  两条降级都不用重写布局，`WidgetRow` 加一个 `dense` 单行档即可

## 资讯日期块：衬线海报式（0.31.2）

参考图给的样式：圆角方块 + 顶部小号年份（下方一条细横线）+ 大号 `MM.DD`，
整体高对比衬线，像一张日期海报。现状是另一套：

| | 现在 `DateStamp` | 参考图 |
|---|---|---|
| 尺寸 | 56dp 方块 | 约「年:数字 = 1:2.6」的比例，需要 72~80dp |
| 年版式 | 左上 11sp 无衬线 | 左上小号衬线，**下方一条细横线** |
| 日期版式 | 右下 14sp `MM/DD` | 正下方 22~30sp `MM.DD`，紧贴横线 |
| 分隔 | 一条左下→右上的**斜线**压在文字上 | 竖向层次，无线压字 |
| 底色 | `surfaceVariant` | **跟随主题色**（参考图那个藕粉只是样图背景，不是设计） |

**可行性：高。** 结构（一个方块里放年份 + 日期）已经存在，改的是排版与字体。

### 几个已经查过的硬事实

- **数字已经等宽**：内嵌的 `noto_serif_subset.ttf` 十个数字宽度全是 `559/1000 em`，
  所以 `10.26` 与 `11.03` 宽度一致，不会每行抖动 —— 这是这个版式成立的前提，白送的
- **但句点 `.` 不在子集里**：现状只有 `0-9` 与 `—`（共 11 个字符）。
  直接用 `.` 会 fallback 到系统字体，同一个日期里出现两种字形，非常明显 → **必须重新子集**
- 子集体积 2604 B，加一个句点几乎不涨（估 <3 KB）
- `unitsPerEm = 1000`，字号换算干净

### 真实取舍：字号与行高

按参考图比例，方块要 72~80dp 才撑得开（56dp 里数字只能到 17sp，海报感全无）。
而资讯列表一屏 6~8 条，**每行都顶一个 76dp 大数字会非常吵**，标题反被压住。

**结论：不要照搬到列表的每一行**（当时的两个折中方案都不用了，见下面的定稿）。

> 后记：这条取舍后来被更彻底地解决了 —— **列表干脆不用日期块**（改纯文字日期），
> 日期块只在卡片头出现一次，宽度由卡宽 1/4 反推。所以「字号 vs 行高」这个二选一根本不存在了，
> 见下面「列表视图改传统文字日期」。

### 形态已定：混合双视图（10-29 定）

- **卡片视图**：层叠轮播，左右滑切日期，一卡 = 一天，卡内纵向滚当天推送 —— **默认进入**
- **列表视图**：现有列表（跨天、密度高）+ 顶部可横滑日期胶囊条
- 顶栏右侧一个图标在两视图间切换；两边各自记住自己的位置

#### 列表视图改传统文字日期（10-29 定）

画模拟图时暴露的问题：列表逐行带日期块会出现 `10.29 / 10.29 / 10.28 / 10.28`，
一屏四次同样的数字，纯粹是噪声 —— 日期块本来是视觉重点，重复四次就不再是重点。

**决定：装饰只留在卡片视图，列表回归纯文字。**

参照 QQ 空间的「月标题 + 每条带时间戳」布局（10-29 定第二版）：

- 列表顶部：**`2026 年 10 月` 作为吸顶月标题**（`stickyHeader`），
  **不配日历图标、不做「跳回今天」** —— 列表滚到顶就是最新，多一个按钮反而多一处要维护的状态
- 每条：栏目 chip + 标题，**标题下方一行小字写完整时间 `10-29 14:20`** ——
  年月已在顶部，条内仍写月份是有意的（QQ 空间也这么干）：时间戳是元数据、很小很淡，
  重复一次换来"任何一条都能独立读"，比只写 `29 日` 更稳
- **列表彻底不用 `DateStamp`**：`parseStamp` 只服务卡片头
- **不做成一张张独立卡片**。QQ 空间每条有正文 + 配图 + 点赞评论，内容高度撑得起卡片；
  我们每条只有一两行标题，卡片化会显得空、且一屏从 6~8 条掉到 4~5 条，
  与"列表用于快速扫通知"的定位相反。分隔线 + 行距足够

可行性：**高，而且是净收益**。

- 实现是纯减法：删掉每行一个 67px 方块 + 一次 `Canvas` 绘制，列表滚动更轻
- 文字日期对读屏友好 —— 之前为了防撑破方块，日期块刻意不跟随系统字号，
  现在这块无障碍债直接消失了
- 代价是列表重新变"平"。原注释提过"列表变平之后左边需要视觉锚点"，
  这次改用**吸顶月标题 + 行距**来重建节奏，不再依赖方块
- 吸顶月标题要按 `publishedAt` 先分组再渲染，`stickyHeader` 在 Foundation 1.6 已有，无需新依赖

#### 卡片视图：装饰集中在这里

既然列表变素，卡片就是唯一允许"花"的地方：

- [ ] 卡片头：**只做日期本身**。hero `DateStamp` 左对齐，
      下方小字一行 `今天 · 10-29 14:20`（「今天 / 昨天 / 3 天前」与日期同左对齐、同一行）
      —— **删掉「共 N 条 / 未读 M」**，卡片不需要报数
- [ ] 日期块宽度 = **卡内宽 × 0.25**（不是固定 80dp），字号按这个宽反推到最大；
      右侧 3/4 永远留给内容，日期再怎么放大也不许越界
- [ ] 卡内条目分主次：**当天第一条用大标题**（16sp/500，最多 2 行），
      其余用小标题（13sp），条形上更紧凑 —— 一天之内的"头等重要"
- [ ] 卡片底色用主题色渐变，但**要明显看得出是渐变**：现在 `SeedColor` 衍生的两档
      色差太小、叠出来接近纯色。做法是在 `SeedColor` 上另派生一对**高饱和端点**
      （提高 saturation、拉开明度差约 12~18%），仍然由种子色推出、不写死色值；
      亚克力只在 App 内可用，widget 不行，别混
- [ ] 卡片圆角 24dp + 1dp 内侧高光边（深色下代替阴影）
- [ ] 切换日期时卡片整体轻微下沉 → 回弹，与层叠位移同一驱动值，不要另起一个动画

#### 顶栏按钮：删哪个要分清（**待确认**）

现在顶栏有两个图标：**视图切换** 与 **刷新**。下拉刷新本来就存在，所以"多余"的
更可能是刷新按钮；而视图切换删掉之后就没有入口了。

- [ ] 方案 A（建议）：只删**刷新**按钮，保留视图切换（一个 16dp 图标）
- [ ] 方案 B：两个都删，视图切换改成标题右侧的小分段 `卡片 · 列表`
- [ ] 方案 C：两个都删，靠手势切 —— 但卡片里左右滑已被"切日期"占用，
      跨视图手势必然打架，**不建议**

#### 层叠式：先说清楚能不能做到「真叠」

**做不到真遮挡。** `HorizontalPager` 是并列排布的，子项之间不能互相压，
所以"后一张卡被前一张盖住 30%"这种效果在 pager 里没有正解。

能做的是**近叠**：靠当前页偏移连续驱动 `scale` / `alpha` / `translationY`，
观感是"一叠牌被推开"，而不是"一叠牌相互遮挡"。

| 参数 | 值 |
|---|---|
| 卡片宽 | 屏宽 − 64dp（左右各露 32dp） |
| 圆角 | 24dp |
| `pageSpacing` | 12dp |
| 相邻卡 scale | 0.92 |
| 相邻卡 alpha | 0.55 |
| 相邻卡上移 | 10dp |
| 预合成 | `beyondBoundsPageCount = 1`，再远的 alpha 归零 |

若之后坚持要真叠（前卡遮后卡），只能弃用 pager、自绘 `Layout` + `Animatable` 偏移，
手势、吸附、无障碍全要手写，成本约 3~5 倍且边缘 case 多 —— **不建议**。

#### 切换动画规划

分五处，前两处是重点：

- [ ] **卡片内横滑**：`currentPageOffsetFraction` 1:1 跟手驱动 scale/alpha/offset，
      **不用 spring** —— 跟手才有的"推牌"手感，松手后交给 pager 的 snap 收尾
- [ ] **卡片 ⇄ 列表**：`AnimatedContent` + 垂直错位（卡片上移淡出 / 列表下方淡入，
      反向对称），220ms、`FastOutSlowIn`。
      **不做共享元素**（container transform）：Compose 没有官方实现，手写要测量两棵树，
      收益只是"更花哨"，碎了很难修
- [ ] **卡片 → 详情**：沿用现有 `bounds` 从行位置长出的展开动画，卡片内条目同样记录 bounds
- [ ] **列表滚动联动**（可选增强）：卡片视图作为列表的 header，随滚动收缩 —— 
      这样"切换"在滚动路径上也被消解掉一部分
- [ ] **日期胶囊条**：选中项宽度/字重/底色过渡 180ms，与周次栏同一套 spec

#### 横滑提示：自动浮现 → 摇晃 → 自动消失（**完全独立的一条动画**）

静态提示不够，用户第一眼未必知道能左右滑。要求：**空闲一会儿自动浮出、左右晃一下、
再自己消失；手指一碰立刻消失；这条动画不与任何其他动画绑定。**

- [ ] 触发：进入卡片视图后 `idle 2.5s` 且 `pagerState.isScrollInProgress == false`
- [ ] 进场：文字 + 左右箭头淡入 200ms、上浮 6dp
- [ ] 摇晃：位移序列 `0 → +6dp → -6dp → +4dp → -4dp → 0`，总 700ms，
      用 `keyframes` 的 `Animatable`，**easing 用线性**（摇晃带缓动会显得飘）
- [ ] 停留 900ms 后淡出 300ms
- [ ] **任一触摸/滑动立即淡出**（`pointerInput` 的 `awaitPointerEventScope` 只监听 down，
      不消费手势，否则会抢掉 pager）
- [ ] 一次会话只提示一次：用 `rememberSaveable` 记「已提示」，
      跨进程用 DataStore 记「看过新手提示」，看过就不再摇
- [ ] **独立实现**：单独 `LaunchedEffect(Unit)` + 自己的 `Animatable`，
      **不读 `currentPageOffsetFraction`、不挂在 pager 的 state 上** ——
      否则用户滑动时它会被连带动，正好违反"滑了就消失"
- [ ] 文案只写「左右滑切换日期」，不要写「共 N 天」（天数会变，提示不该带数据）

#### 落地时要守的几条

- [ ] 卡片高度固定 = `屏高 − 顶栏 − 提示/页码区`，**不要按内容自适应** ——
      否则每页高度不同，横向滑动时容器高度跳动
- [ ] 两视图各自保存状态：`rememberSaveable` 存 pager 当前页 与 列表 `LazyListState`，
      来回切换不能丢位置
- [ ] 切视图时若列表状态丢失，用户会以为"刷没了" —— 这条比动画本身更重要
- [ ] 深色模式下相邻卡 alpha 0.55 会糊成一片 → 用 hairline 描边区分层次，别只靠阴影
      （`Modifier.shadow` 在深色底上几乎不可见）

### 落点：`DateStamp` 宽度由卡片算，不写死

列表不用它之后只剩卡片头一个调用点。尺寸也不再拍死，**由卡内宽反推**：

`日期块宽 = 卡内宽 × 0.25`（卡内宽 316dp 时约 79dp；换机型自动缩放）

| 元素 | 比例（相对日期块宽） | 316dp 卡内的值 |
|---|---|---|
| 年 | 0.15 | 12sp |
| 细线 | — | 1dp 高，宽 ≈ 年宽 × 1.3 |
| 月日 | 0.27 | 21~22sp |
| 内边距 | 0.10 | 8dp |
| 行高 | fontSize × 1.05 | 收紧，衬线体上下留白大 |

- [ ] `DateStamp(size: Dp)`：**必须传 size**，由调用点算好（`卡内宽 × 0.25`）；
      不给默认值，避免以后又出现"随手调一个 80dp"的写死值
- [ ] 日期块下方一行小字（与日期同左对齐）：`今天 · 10-29 14:20`
      —— 「今天 / 昨天 / N 天前」放最前，再接月日时分
- [ ] 排布改垂直：年（左上，宋体小字）→ 细线（左对齐）→ 月日（左下，宋体大字）；
      **删掉原来的斜线与右下角定位**
- [ ] 细线宽度用 `onTextLayout` 取年份实际宽度 × 1.3 —— 固定百分比会让
      「2026」和「9999」的线看起来不一样长
- [ ] 字号固定 sp、不跟随系统字体缩放：这是图形元素不是正文，跟随后会撑破方块；
      `maxLines = 1` + `softWrap = false` 兜底，`contentDescription` 写完整日期补无障碍
- [ ] `res/font/`：重跑 `tools/subset-font.py` 加 `.`（现子集只有 `0-9` 与 `—`）
- [ ] 数字 `letterSpacing = (-0.5).sp`，衬线体默认字距偏散
- [ ] 底色由 `SeedColor` + `DarkMode` 推出，**不得写死色值**；深色下自然变暗而非反白
- [ ] 若当天日期解析失败：卡片头退化成纯文字日期，**不要不画** ——
      卡片头缺一块比显示朴素文字更难看

> 对比度温和得多。照抄版式能得到"杂志感"，但拿不到图里那种刀锋感 ——

## 增量更新：App 更新器 + 资源包（0.32.0）

**结论：APK 层面没有「不安装」的更新。** Android 的更新模型就是「装新包覆盖旧包」，
差分包（bsdiff/bspatch）只减少下载体积，安装这一步省不掉。
真正能省掉安装的是**内容外置**。

**先澄清一点**：覆盖安装**不会丢数据**。同签名 + `versionCode` 递增即可原地升级，
Room、DataStore、课表都在。只有签名变了或卸载重装才会清空 ——
所以「更新要重装」不等于「要重新导课表」。

| 方案 | 要不要装 | 省多少 | 代价 | 结论 |
|---|---|---|---|---|
| A 完整 APK 覆盖安装 | 要 | 0 | 2.1MB | 做，这是底座 |
| B 差分包 bspatch | **要** | 30~60% | patch 矩阵 + 合成失败回退 | **不做** |
| C 内容外置（远程 JSON） | **不要** | 100% | 版本号 + 校验 + 离线兜底 | **做** |

B 不做的理由：2.1MB 的包顶多省 1MB；用户可能从 0.30.2 直接跳 0.32.0，
要么存 N×(N-1)/2 个 patch，要么做链式（任一环坏整条失效），再叠上签名校验、
合成后安装失败的回退 —— 维护成本远超收益。

### C 的落点：哪些内容该外置

| 资源 | 现状 | 外置价值 | 变动频率 |
|---|---|---|---|
| **资讯源与正文规则** | `NewsSource` / `NewsCrawler` 里的栏目与选择器 | **最高**：学校改版即失效，现在只能发版 | 不定期 |
| **课表解析词典** | `FieldExtractor` / `TextTimetableParser` 的表头词与正则 | **最高**：各学院导出格式不一，可随反馈持续补 | 持续 |
| **校历 + 作息模板** | `assets/calendar/nbu_calendar.json` | 高：每学年必变，「第几周」全靠它 | 1~2 次/年 |
| 开学日期推定规则 | `TermStartResolver` 的关键词与规则 | 高：校历抓不到时全靠它 | 1 次/年 |
| 入口列表 | `assets/portal/entries.json` | 高：换域名、加系统 | 不定期 |
| 服务公告 | 无（新增 `notice.json`） | 中：开学季提示、维护通知 | 不定期 |
| 许可清单 | `assets/licenses/index.json` | 低：换依赖才动 | 极低 |
| 提示文案 | 现在硬编码在 Kotlin 里 | 低：改文案仍建议发版，否则和截图/文档脱节 | — |

**必须不外部化的三类**：

- **域名白名单与安全策略** —— 根必须在内置代码里，否则远程包能把用户导到任意地址
- **用户数据** —— 课表、自定义作息、设置，这些是本机状态，不是资源
- **解析算法本身** —— 只外置「词典 / 选择器 / 关键词」，不外置代码

### 版本规则：资源独立版本，单向兼容

- [ ] 单一资源包 `pack`，版本号用 **`yyyyMMddHHmm`（如 `202610291248`）** ——
      照 MAA 的做法：**版本号本身就是时间**，精确到分钟，人一眼能看出新旧；
      与 App 的 `versionName` 完全解耦，资源发多少次都不影响 App 版本
- [ ] 为什么精确到分钟而不是只到日期：两个包在同一天发两次是常态
      （上午修入口、下午补资讯源），只到日期就会撞版本、被迫加序号；
      也不用精确到秒 —— 同一秒发两个包不现实，而 12 位已经够短
- [ ] `version` 用 **Long** 存（12 位，远小于 `Long.MAX`），比较直接比 Long，不要比字符串；
      展示时格式化回 `2026-10-29 12:48`，不要让人读 `202610291248` 这种 12 位连写
- [ ] 与 `updatedAt` / `notes` 的分工：`version` 只用于比较排序；
      `updatedAt`（ISO 8601）与 `notes`（这次改了什么）只用于展示 ——
      `updatedAt` 进「数据与诊断」，`notes` 进应用内更新日志的「资源更新」块。
      **三者不能混用**：拿 `updatedAt` 去比大小，只要服务端换时区就可能出现"版本倒退"
- [ ] pack 内每个文件带 `sha256`；**整个 pack 的 sha256 写在 APK 内置的 manifest 里**
      （包内自带的清单不算数，否则等于包自证清白）
- [ ] **只升不降**：`remote.version > local.version` 才应用，更旧的包一律拒绝
- [ ] **资源不向下兼容**：pack 声明 `minAppVersion`（对应 `versionCode`），
      当前 App 低于它就整体跳过，**不做部分应用** —— 半套新资源比不更新更糟
- [ ] **新 App 必须读得动旧资源**：schema 只增字段、不改语义、不删字段；
      要删字段就等最老的支持版本整体淘汰。`assets/` 内置包永远能跑，这是底线
- [ ] 应用失败（校验 / 解析 / 结构不符）→ 回退内置包，记 `[Pack] 回退 原因=...`，
      同一版本不再重试，避免每次启动都卡一次
- [ ] 「数据与诊断」页显示当前 pack 版本与来源（内置 / 下载），反馈时一眼能定位

### 版本检查与资源检查必须分开

三条理由，任何一条都足以让它们不能合成一个「检查更新」：

| | App 版本 | 资源包 |
|---|---|---|
| 动作 | 下载 APK → **跳系统安装器** → 用户确认 | 下载文件 → 写私有目录 → 静默生效 |
| 节奏 | 低频、手动为主（一天/一周一次） | 高频、后台自动（每次启动都可能） |
| 失败后果 | 装到一半失败，用户看得见 | 静默失败，用户只看到「资讯空了」 |
| 版本号语义 | `versionCode` 单调递增 | `yyyyMMddHHmm` 时间戳式 |

合成一个的后果很具体：用户点了「检查更新」，结果只是资源变了、App 没变，
他会以为更新坏了；或者反过来，一个 200KB 的资源包让他以为要装 2MB 的包。

- [ ] 两个检查器、两套状态：`AppUpdateChecker`（GitHub Release 的 `manifest.json`）/
      `ResourcePackChecker`（pack 的 `latest.json`），互不调用
- [ ] 两处 UI：版本 →「关于」页显式「检查更新」+ 更新说明 + 是否安装由用户决定；
      资源 → 只出现在「数据与诊断」里（当前 pack 版本 / 来源 / 上次检查时间），**不弹窗**
- [ ] 两条日志：`[Update] ...` 与 `[Pack] ...`，不要混写成一条「检查更新」，
      否则出问题时看不出是哪一层
- [ ] 两个节奏：版本检查**每 24 小时最多一次**且只在用户进入「关于」时触发；
      资源检查在启动后延迟 8~10 秒（避开首屏合成与新闻抓取），成功即应用
- [ ] **失败互不影响**：资源检查挂了不能让版本检查沉默，反之亦然
- [ ] 资源被 `minAppVersion` 挡住时，**只记日志、不串联到版本 UI**。
      一旦写成「有新版本可解锁新资源」，两个状态机就被绑在一起，
      以后每次改资源都要考虑怎么提示升级 App
- [ ] **共享的只有基础设施**：HTTP 客户端、ETag 缓存、镜像 fallback、sha256 校验、
      版本比较工具。共享工具，不共享状态机 —— 这是「分开做」的边界

### 参考 MAA 的资源更新（实地看过其实现，10-29）

MAA 能"不重装就更新"的根本原因：**它的资源是 `resource/` 目录，不是安装包**，
更新就是覆盖文件。Android 的 APK 是签名整体，这条在客户端上照搬不了；
但它的**分发机制**几乎可以整套搬给「内容外置」。

可以直接抄的六条：

- [ ] `version.json` 里用 **`last_updated` 时间戳**当版本号，不搞语义版本 ——
      MAA 就是这么做的（`resource/version.json`），比较大小、生成、迁移都最省事
- [ ] **拒绝比当前更旧的包**。MAA 明说"不会导入比当前更旧的包"。
      我们原来只想到 `minAppVersion`（防新包发旧端），缺的反向保护是"防旧包覆盖新数据"
- [ ] **ETag / If-None-Match 条件请求**（MAA 的 `Helper/ETagCache.cs`）：
      版本没变时服务端回 304 无 body，比每次都下 `version.json` 更省。jsDelivr 支持
- [ ] **镜像列表逐个 fallback**：MAA 把 GitHub Release 链接和镜像一起塞进候选地址。
      我们对应 GitHub raw → jsDelivr → 内置，三级
- [ ] **增量包只合并不删除**：MAA 的资源包是"增量内容，不删原有文件"。
      所以远程包必须按文件合并，绝不能"用远程目录整体替换本地目录"
- [ ] **全量包兜底**：MAA 的 GitHub 路径就是下全量 zip 解压合并；
      增量包损坏或校验失败时，要能退回全量

明确不抄的两条：

- ❌ **客户端文件级 OTA**：MAA 是 Windows/Linux 便携程序，覆盖 exe/dll 即可；
      Android 只能整包签名安装，没有对应物
- ❌ **MirrorChyan CDK 付费 CDN**：MAA 的增量通道靠这个，我们不能引入付费依赖

一个参考数值：MAA 的资源有几十 MB，文件级增量收益显著；我们的 `assets/` 只有 64KB，
**逐文件增量的流量收益可以忽略**，抄它的价值在"机制正确"（版本、校验、回退、镜像），
不在"省流量"。

### 现成模板：MaaMeow 的「双层更新」

仓库 `Aliothmoon/MAA-Meow`。**本体与资源是两条更新通道**：

| 层 | 怎么更新 | 要装吗 |
|---|---|---|
| APP 本体（含 MaaCore）| GitHub Release 下 APK 覆盖安装 | **要**（arm64 177MB / universal 199MB） |
| 资源（`resource/`）| 应用内直接下载资源包到应用私有目录 | **不要** |

这一点很重要 —— 我上一版据 Release 里「内置 MaaCore 升级至 v6.20.0」推断它"没有独立资源更新"，
**是错的**：core 跟包走，资源不跟包走。改一条资源不需要重下 177MB。

它的资源更新之所以能免安装，只有一个原因：**资源落在 `filesDir`，不在 APK 里**。
这跟桌面版 MAA 是同一个模型，只是换了个落点。

对我们最直接的四条启发：

- [ ] **双层更新是 Android 上唯一能"免安装"的形态**：体走 APK，内容走文件。
      这比"减少安装包体积"重要得多 —— 少装一次，就少过一次「安装未知应用」那道坎
- [ ] **APK 内置一份 + 允许更高版本覆盖**：MaaMeow 的包里带一份资源，
      所以首次启动不联网也能用。我们的 `assets/` 正好就是这个角色，不用改结构
- [ ] **资源包格式与端无关**：桌面 MAA 和 MaaMeow 吃同一套 zip + `version.json`。
      我们的远程包也应如此，将来做桌面端/网页端可直接复用
- [ ] **免安装顺带免权限**：APK 更新在 MIUI / ColorOS 上要用户单独开「安装未知应用」，
      资源更新则只是写自己目录 —— 这是两条通道体验差的根源

**我们比它多一层风险，必须额外处理**：MaaMeow 的资源是游戏数据，改坏了只是功能异常；
我们的 `assets/portal/entries.json` 是**跳转 URL 列表**。远程包一旦被篡改，
可以把用户导到钓鱼页面。所以内容外置必须比 MAA 更严：

- [ ] **下载源写死在 APK 里**（GitHub raw → jsDelivr 两条），不接受远程包自己指定新源
- [ ] 远程包整体 **sha256 必须在 APK 内置的 manifest 里**（而不是包内自带的清单），
      否则"包自证清白"没有意义

# 验收方式：能用导出日志判的，就不走 ADB

现状：验收基本靠「ADB 连机 → 手工点 → 看屏幕」，设备一掉线整轮验证就停摆（0.30.3 就是这样）。
但界面上真正需要眼睛的只有**间距、颜色、对齐**；剩下的「点完发生了什么」「状态变没变」
都能由应用自己写进工作日志 —— 用户导出、贴过来，我读日志判定，零连接成本。

## A. `AppLog` 加结构化事件

`util/AppLog.kt` 只有 `log(tag, message)` 自由文本，靠拼字符串，不好 grep。

- [ ] 新增 `AppLog.event(tag: String, name: String, vararg fields: Pair<String, Any?>)`，
      输出 `[tag] name key=value key=value`；单条仍受 500 字符上限约束
- [ ] 加 `AppLog.assert(tag: String, name: String, ok: Boolean, detail: String)`：
      `ok=false` 时以 `[Assert]` 前缀落一条，和普通记录区分开

## B. 关键交互打点（每条都替代一次 ADB 手点）

- [ ] 周次跳转（`TimetableScreen`）：请求时打
      `[Nav] 请求 目标=8 来源=本周|箭头 基准=1 距离=7 方式=瞬移|动画`，
      落位时打 `[Nav] 落位 8 耗时=63ms` —— 这次的「本周只生效一次」用这两行就能抓到
- [ ] 提醒开关（`ReminderCard`）：`[Set] reminder on|off 来源=卡片`、
      `[Set] live on|off`、渠道状态每次变化打一条（现在只在页面打开时回显，不进日志）
- [ ] 后台运行跳转（`BackgroundRunCard`）：`[Sys] 跳转 自启动|电池策略 成功|回落`
- [ ] 入口页（`PortalScreen`）：`[Portal] 点击 id=C3 结果=浏览器|复制|校历`，
      只记 id 与结果，**不记课程名、不记 URL**
- [ ] 页面进出（`AppRoot`）：`[UI] 进入 设置/提醒` / `[UI] 返回 课表`
- [ ] 主题（`AppearanceScreen`）：`[Set] seed=blue dark=follow backdrop=grad1`

- [ ] `[Nav]` 请求后 800ms 内无落位 → `[Assert] nav.stuck 目标=8`
- [ ] 落位页 ≠ 目标页 → `[Assert] nav.mismatch 期望=8 实际=7`
- [ ] 验收清单直接写「**日志里不得出现任何 `[Assert]`**」，一条都不用人工盯

`AppLog.dump()` 现在是纯流水，读的人要从 27 行里数。在正文前加 8～10 行汇总：

- 运行时长、启动次数、切周次数（其中瞬移 N 次）、
  `[Assert]` 计数（0 才正常）、提醒重排次数、`[Perf]` 最差一次掉帧
