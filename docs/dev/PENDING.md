# 一、更新提醒持久化（P1）

参考 MAA-Meow 的机制：**检查到新版本就立刻写 DataStore，与下载安装解耦**；
只有装上的版本号与记录对得上才弹更新内容；弹过之后搬到另一份留档，供关于页回看。

现状：`UpdateCenter` 的检查结果只存在 `MutableStateFlow`，进程结束即消失；
「关于」页弹出的更新说明是**远端最新版**的内容，不是用户这次实际装上的版本。

- [ ] `SettingsStore` 增加三键：`pendingAppVersion` / `pendingAppNotes` / `currentAppNotes`
- [ ] 检查到新版本且 `notes` 非空 → **立即写 pending**，不等下载结果
- [ ] 下载失败、安装失败、用户取消，一律不清 pending
- [ ] 启动时 `pendingAppVersion == BuildConfig.VERSION_NAME` → 弹「本次更新内容」，
      并把 pending 搬运到 current
- [ ] 搬运在单次 `edit {}` 内完成（两份不同步比丢一份更糟）
- [ ] 「关于 → 文档」加「本次更新内容」入口，读 current，可反复回看
- [ ] 检查更新弹窗文案改为「将升级到 x.y.z」，不再暗示这是当前版本的说明
- [ ] **[日志]** `[Update] 记录待装 x.y.z`、`[Update] 已装 x.y.z 展示更新内容`

**明确不做系统通知**：加通知要多处理渠道关闭、免打扰、权限被拒一串分支，
而本应用的打开频率足够覆盖启动弹窗这一条路。

# 三、课表截图 OCR（P2）

课表导入的第三条路。**与已落地的签到码识别是两条线，别混为一谈**：

| | 签到码识别（已做） | 课表截图 OCR（未做） |
|---|---|---|
| 目标 | 从一帧画面里找 4 位数字 | 从一张截图里还原整张课表 |
| 输入 | 相机实时流 | 相册图片或截屏 |
| 难点 | 颜色定位 + 倒计时内出结果 | **表格结构还原** |
| 输出 | 一个字符串 | 结构化的 `TimetableEntry` 列表 |

底座已经有了：`com.google.mlkit:text-recognition-chinese:16.0.1` 是 bundled 版，
模型随包走、离线可用，**不用再引第二个 OCR 引擎**。

- [ ] 复用 `SignImagePreprocessor` 的降采样与增强思路，但**不要复用颜色定位** ——
      课表没有「蓝色环境里的黄块」这种特征，按颜色找必然找错
- [ ] 直接吃 ML Kit 的 `Text.TextBlock` 全量结果，交给结构还原
- [ ] **结构还原是唯一真正的难点**：合并单元格、节次列、`1-16周(单)` 这类注记、
      连堂课（3-4 节合并成一个块）。可复用 `parser/GridParser`、`FieldExtractor`
      已有的周次与节次正则
- [ ] 必须有**预览校正**：识别 → 展示可编辑的解析结果 → 用户确认 → 入库。
      跳过这步，识别错一个字比手动输入更烦
- [ ] 先只支持一种版式（教务系统周视图），跑通再扩
- [ ] **[日志]** `[Ocr] 课表 行=8 列=7 课程=23 修正=2`，**不记课程名**

# 十一、其余（P4）

## 技术栈迁移：Flutter（候选，需你拍板）

**动机**：动效与 UI 材质的上限、开发灵活度与适配性。这不是「哪个语言更好」，
而是**这个应用往后靠什么取胜**的问题 —— 如果重信息的工具属性已经够用，
接下来拼的就是观感与手感。

**先摆一个被忽略的事实**：Compose 并不是做不了材质，`graphicsLayer` + `RenderEffect`
（API 31+）能做模糊与着色器，但**兼容性随系统版本断档**，低版本直接降级。
Flutter 自绘整帧，同一套效果在不同机器上表现一致 —— 这正是「适配性」三个字的含义。

现状规模（2026-10-31 实测，89 文件 18,283 行）：

| 层 | 文件 | 行数 | 占比 |
|---|---|---|---|
| `ui/` | 35 | 10,392 | **57%** |
| `data/` | 24 | 3,927 | 21% |
| `parser/` | 11 | 1,055 | 6% |
| `domain/` | 5 | 793 | 4% |
| `widget/` | 3 | 719 | 4% |
| `util/` + 其它 | 11 | 1,397 | 8% |

结论：**要换的只有 UI 那 57%**。数据、解析、分发、通知、小组件（约 8,000 行）留在原生。

三条路线：A 全量重写（成本最高，单向门）／**B 混合 add-to-app（推荐）**／C 不换。
推荐 B 的理由不是「折中」，而是它把不可逆的部分压到最小 —— 数据层、解析器、小组件一行不动，
做不下去还能一页一页退回来。

分阶段：阶段 0 先把与框架无关的部分做扎实（资源包、解析自检、错误可见，换框架也得有）；
阶段 1 用 add-to-app 只做一个页面（建议资讯卡片，动效最密、逻辑最轻、失败可回退）；
阶段 2 铺开，小组件/通知/解析器保持原生。

**决策门（不达标就不铺开）**：

1. 试点页面冷启动增量 > 400ms → 停，「打开就看课表」的定位撑不住
2. 包体增量 > 8MB → 停，2.8MB 涨到 11MB 会抬高「未知来源安装」的犹豫
3. 单页 MethodChannel 往返 > 20 次 → 重新评估边界，别把原生当数据库用

必须一起解决：小组件仍走 Glance（Flutter 无官方 AppWidget，`updateAll` 时机要重设计）、
通知与闹钟留在原生、双引擎内存要在 4GB 低端机实测。

版本号：架构级变更按规则要动主位，我不自行决定。倾向 `0.40.0` 起（继续 0.x），
`1.0.0` 目前给不出「功能定型」的承诺。

## 已发布：0.32.4 字体不随系统缩放

根因：`sp = dp × fontScale` 跟随系统放大，而卡片高度写死 dp，字号变大容器不变就被裁。
修法：固定高度容器内的字号统一走 `fixedSp(v) = (v / fontScale).sp` 反向补偿。
不做：全局禁用 fontScale（会牺牲无障碍设置）。

## 已发布：0.33.x–0.35.x 更新通道

- APK 层面没有"不安装"的更新；能免安装的只有内容外置
- 差分包（bsdiff）**不做**：2MB 的包省不了多少，patch 矩阵与回退成本远超收益
- 固定签名是硬前提：debug keystore 按机器生成，CI 每次不同 → 包永远盖不上旧版
- 清单走 `api.github.com`（实时），文件走 CDN（路径带版本号，不可变）：
  **"现在最新是第几版"这件事不能缓存**
- 失败分两类：网络原因不记 `failedVersion`，只有内容原因才拉黑，且 6 小时后允许重试
- 资源包版本号用 `yyyyMMddHHmm`（Long），只升不降，`minAppVersion` 挡旧端
- 两个检查器互不调用，日志分 `[Update]` / `[Pack]`
