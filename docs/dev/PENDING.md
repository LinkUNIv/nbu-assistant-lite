# 十、点名模块的界面与切换体验（0.37.13，P1）

三项都是真机试用后反馈的，都不碰数据、认证与网络，只动 `browser/` 的界面层与切换时机。

## 10.1 退出按钮：单开一页却是浏览器后退语义

现状顶栏是「返回 / 刷新 / 导出日志」，其中「返回」等价于 `web.goBack()`，系统返回键同样如此。
可这个 Activity 是单开一页，网页历史属于考勤站自己 —— 于是「想退出点名」被解释成
「在考勤站里后退一步」，用户要连按好几次才回得到课表。

- [ ] 顶栏左侧改为「关闭」，直接 `finish()`，与网页历史无关
- [ ] 「返回」（网页后退）降为图标按钮或收进溢出菜单，保留但不占主位
- [ ] 系统返回键保持网页后退语义，但落到 `h5/student/schedule` 时再按一次即 `finish()`
- [ ] 溢出菜单收纳「刷新 / 导出日志 / 学校原页面」

**顺带要解决的效率问题**：`onDestroy` 现在无条件 `web.destroy()`，退出即销毁，
下次进点名要重新加载整个 Nuxt 应用。预加载等于白做。

- [ ] `PreloadedPage.release(web)`：把 WebView 摘下、塞回 1dp 隐形宿主，与 `claim()` 成对
- [ ] 仅在「预加载开启 + 当前 URL 仍在 `attendance.nbu.edu.cn`」时交还，其余照旧销毁
- [ ] 交还前 `cancelSignInput()` 并复位 `AttendanceSignal`

## 10.2 深色模式下切换时原网页闪现（已淡出，保留三项观察）

**2026-11-10 复核：视觉层面已不闪。** 0.37.11 把 `root`、`browserFrame`、`web` 背景与
`panel` 底色统一到 `attendanceBackground()`，即使网页先露出来也同色，跳变看不出来。
下面五条成因里第 4 条已彻底解决，其余三条仍在，只是被同色底掩盖。

共同点是**「先画后遮」**：自绘面板是事后盖上去的，中间总有一段时间网页是可见的。
按可能性排序：

| # | 原因 | 证据 | 现状（11-10） |
|---|---|---|---|
| 1 | 切换时机只由轮询决定 | `poll` 在课表页 250ms、其他页 1000ms 一次；考勤站是 Nuxt SPA，站内跳转不触发 `onPageStarted` | ❌ 仍在。`onConsoleMessage` 只记日志，没调 `inspect()` |
| 2 | `!trusted()` 无条件 `reveal()` | 「非认证页就把 WebView 显形」，中间页会露出原网页，下一拍再遮回去 | ⚠️ 收敛为 `if (panel != null) reveal()`，仍会在面板撤销后露一次 |
| 3 | 用 `web.alpha` 做隐藏 | `setAlpha` 在某些 WebView 版本晚一帧生效，也不是硬遮挡 | ❌ 仍是唯一手段；同色底让它看不出来 |
| 4 | 底色有两个来源 | 快照未写时窗口与 WebView 会按系统深浅取色 | ✅ **已解决**：0.37.11 四处统一走 `attendanceBackground()` |
| 5 | 签到成功整页 `loadUrl` | 回课表用 `loadUrl(SCHEDULE)`，Nuxt 整个重启 | ❌ 仍在。同色底后是「深色空屏」而非白屏 |

**以下为兜底方案，真机再有残留才做**：

- [ ] **加不透明遮罩层**：`browserFrame` 内、WebView 之上放一个普通 `View`，底色跟主题，
      默认可见，只有 `reveal()` 才移开。不再依赖 `web.alpha` 隐藏
- [ ] **路由变化立刻切换**：`OBSERVER` 已 hook `pushState/replaceState/popstate/hashchange`
      并发出 `NBU_TRACE`。在 `onConsoleMessage` 里对这四个 kind 调 `routeChanged()` → 立即
      `inspect()`，把延迟从「最多 1 秒」压到「一帧」，轮询只作兜底
- [ ] **`!trusted()` 不再自动 `reveal()`**：改为显示「需要在原页面继续」面板，
      用户点按钮才显形，与「查看学校原页面」是同一个动作
- [x] **配色单一来源**：`AttendanceTheme` 的 `dark` 值统一驱动（0.37.11）
      `root` / `browserFrame` / `web` / 窗口底色，去掉 `attendanceBackground()` 的快照读法
- [ ] **签到成功改用页面内返回**：`history.back()` 或站内路由，不整页重载

**验收**：深色模式下反复进出点名页、在课程列表与签到页之间来回切换，
录屏逐帧检查，不得出现任何原网页内容。

# 十二、其余（P4）

## 技术栈迁移：Flutter（候选，需你拍板）

**动机**：动效与 UI 材质的上限、开发灵活度与适配性。这不是「哪个语言更好」，
而是**这个应用往后靠什么取胜**的问题 —— 如果重信息的工具属性已经够用，
接下来拼的就是观感与手感。

**先摆一个被忽略的事实**：Compose 并不是做不了材质，`graphicsLayer` + `RenderEffect`
（API 31+）能做模糊与着色器，但**兼容性随系统版本断档**，低版本直接降级。
Flutter 自绘整帧，同一套效果在不同机器上表现一致 —— 这正是「适配性」三个字的含义。

现状规模（2026-10-31 实测，89 文件 18,283 行）：

| 层 | 文件 | 行数 | 占比 |
|---|---|---|---|
| `ui/` | 35 | 10,392 | **57%** |
| `data/` | 24 | 3,927 | 21% |
| `parser/` | 11 | 1,055 | 6% |
| `domain/` | 5 | 793 | 4% |
| `widget/` | 3 | 719 | 4% |
| `util/` + 其它 | 11 | 1,397 | 8% |

结论：**要换的只有 UI 那 57%**。数据、解析、分发、通知、小组件（约 8,000 行）留在原生。

三条路线：A 全量重写（成本最高，单向门）／**B 混合 add-to-app（推荐）**／C 不换。
推荐 B 的理由不是「折中」，而是它把不可逆的部分压到最小 —— 数据层、解析器、小组件一行不动，
做不下去还能一页一页退回来。

分阶段：阶段 0 先把与框架无关的部分做扎实（资源包、解析自检、错误可见，换框架也得有）；
阶段 1 用 add-to-app 只做一个页面（建议资讯卡片，动效最密、逻辑最轻、失败可回退）；
阶段 2 铺开，小组件/通知/解析器保持原生。

**决策门（不达标就不铺开）**：

1. 试点页面冷启动增量 > 400ms → 停，「打开就看课表」的定位撑不住
2. 包体增量 > 8MB → 停，2.8MB 涨到 11MB 会抬高「未知来源安装」的犹豫
3. 单页 MethodChannel 往返 > 20 次 → 重新评估边界，别把原生当数据库用

必须一起解决：小组件仍走 Glance（Flutter 无官方 AppWidget，`updateAll` 时机要重设计）、
通知与闹钟留在原生、双引擎内存要在 4GB 低端机实测。

版本号：架构级变更按规则要动主位，我不自行决定。倾向 `0.41.0` 起（继续 0.x），
`1.0.0` 目前给不出「功能定型」的承诺。

# 十三、发布流水线：同 tag 两条 release（已加固，留观察）

0.37.1 那次同一 tag 下出现了**两条 release**：一条已发布但 0 资产，一条草稿带 6 个资产，
创建时间在同一秒。善后更糟：删掉那条已发布的空壳后，tag 被**不可变发布**机制锁死，
再建 release 一律 422，连删 tag 重建也不行，那个版本号只能作废。

**2026-11-10 复查结论**：现存日志无法定论谁建了第一条（那次 run 的记录已过期，
被删的 release 也查不到）。但工作流有个结构性缺口 —— `release` job 只在推 tag 时跑，
**没有并发组**。同一个 tag 被推两次（重打标签、失败后重跑）就会发出两条创建请求，
而 GitHub 对同 tag 的并发创建不保证原子互斥，这与「同一秒两条」的现场吻合。

已加三道闸（下一次发版起生效）：

- [x] `concurrency: group: release-${{ github.ref }}`：同 tag 发布串行化
- [x] 创建前幂等检查：已存在**已发布**的同 tag release 直接失败（提示改版本号，不要删）；
      已存在**草稿**则复用并覆盖资产
- [x] 发布后自检：`gh api` 断言「恰好一条 + 非草稿 + 资产 ≥ 6」，不满足让任务红着，
      而不是留个半成品给人去发现
- [x] 写进流程：**一条已发布的空 release 比没有 release 更糟**，删它会锁死 tag；
      发现重复时宁可换版本号

- [ ] 观察：下一次发版确认自检通过，且日志里没有第二条创建请求

# 十四、更新推送：与 MAA 的差距（0.37.8 / 0.38.2）

用户反馈「MAA 的更新总是更及时」。查了 MAA 官方文档，差距不在实现复杂度，在四处：

| 维度 | MAA | 我们 |
|---|---|---|
| 检查时机 | 启动检查 + 每天固定两点（本地 04:00 / 22:00） | 启动 12 秒后，**24 小时一次**，且只有开 App 才查 |
| 渠道 | stable / beta 分离，按通道取版本 | **完全不看**，只比 `versionCode` |
| 传输 | ETag / Last-Modified 条件请求，304 不重复下载 | 每次全量拉 releases 列表 + manifest，**两跳** |
| 更新源 | GitHub + MirrorChyan CDN，可切换 | 仅 GitHub API，单源 |

## 14.1 渠道过滤（先做，这是 bug）

`AppUpdateChecker` 取 `releases?per_page=1` 的第一条就比版本号，而 manifest 里明明有 `channel`。

后果：协作者在 Preview 之后发一个 Debug 包，Preview 用户会被提示升级到 `app.nbult.lite.debug` ——
包名与签名都不同，装到系统安装器必然失败，还白下几十兆。
0.37.3–0.37.5 就是 Debug 连发、0.37.6 才 Preview，中间任何一天打开 App 的用户都会撞上。

- [x] `per_page` 提到 5，往下找 **`channel` 与当前 `BUILD_KIND` 一致**的最新一条（0.37.8）
- [x] channel 缺失或无法识别时不提示（宁可漏一次，不可推错包）（0.37.8）
- [x] 补单测：`UpdateChannelTest` 6 项（0.37.8）

## 14.2 条件请求（0.38.2，省流量、降限流风险）

现在是「列表 → manifest」两次全量请求，未鉴权 API 每小时 60 次/IP，多人共用网络时容易撞线。

- [ ] 缓存 `ETag` / `Last-Modified` 到 DataStore，请求带 `If-None-Match` / `If-Modified-Since`
- [ ] 命中 304 直接按「无变化」处理，不解析、不下载
- [ ] 304 也要算作「刚检查过」，否则会每次启动都重试

## 14.3 弹窗排版（0.37.8，已实现并编译验证）

- [x] `ChangelogCatalog.parseFragment()`：摘掉一级标题，正文复用块解析
- [x] 弹窗改用 `ChangelogBlockView`，不再把 `**`、`- `、反引号当字面字符
- [x] 正文 12sp → 14sp（bodyMedium），标题 titleSmall
- [ ] 真机看一眼长说明（>800 字）的滚动与行距

## 14.4 定时检查（0.38.2，次位）

只在开 App 时检查，等于「用户不打开就永远不知道」。这是「MAA 更及时」的主因。

已落地一半（0.37.9 / 0.37.12）：启动检查从 12s 提前到 4s、间隔 24h → 6h、
前台恢复复查（`repeatOnLifecycle` RESUMED）并做了 30 分钟日志节流。
剩下的只有「应用没打开时的后台检查」，那才需要 WorkManager。

- [ ] WorkManager 每日一次 + 启动检查（两条路都留，启动那次解决「刚打开就想看」）
- [ ] 仅在联网时跑；失败退避重试，不要每小时重试
- [ ] 与「更新弹窗」开关联动：关掉只记状态不弹，小红点仍然亮
- [ ] 注意省电策略与厂商后台限制，需真机验证（与第八节前台服务是两件事，别混）

## 14.5 明确不抄

**第三方下载镜像**（MirrorChyan 需 CDK，ghproxy 一类不可控）。
sha256 能挡住「下到半截的包」，挡不住「源被整体换掉」—— 后者要靠第二渠道校验签名，我们没有。
若将来国内下载确实频繁失败，再单独评估**自建**静态镜像，而不是接公共代理。

## 14.6 动效方向（0.37.10，P2）

产品口径已定：**包体不是约束**，最终形态是「功能完整 + 动画精美 + 设计感强」，一百兆上下可以接受。
这条推翻了此前「为了体积砍动效」的默认倾向 —— 评估动效时只看两件事：
**有没有明确的使用场景**、**会不会破坏统一节奏**，不再以「多几兆」为由否决。

参考清单与统一口径见 [`docs/design/MOTION.md`](../design/MOTION.md)。要落地的部分：

- [ ] 把散落的 `tween(150/180/220)` 收敛到四档：120 / 180 / 240 / 300ms
- [ ] `page()` 340ms → 300ms（高刷屏上偏拖）
- [ ] 列表项进出统一 `Modifier.animateItemPlacement()`（1.6 的 API，1.7 才改名 `animateItem`）
- [ ] 拖动/吸附改用 `spring(dampingRatio = 0.85f, stiffness = 400f)`，替掉现在的 `snap()` tween
      —— **目前全项目没有一处弹簧**
- [ ] 弹出的面板从来源方向长出来（Balloon 的箭头缩放原点）
- [ ] 列出「哪些地方该有动效、哪些地方必须没有」，避免越加越吵

**允许引入的**：包体放开之后，Lottie / Rive 这类运行时不再是禁区，但必须先有具体用途
（例如启动动画或空态插画），且不替代既有状态动效。**不允许**：引入第二套组件体系。

## 14.7 第三方引用与署名（合规，优先级高于功能）

参考仓库的许可证不统一，直接抄代码会踩线。规则见
[`docs/design/MOTION.md`](../design/MOTION.md) 第七节，要点：

- [ ] **Apache-2.0**（本清单里 8 个）：可以改、可以商用，但分发时必须**保留版权声明与许可证全文**，
      修改过的文件要标注「已修改」。若上游带 `NOTICE`，要一并转达
- [ ] **MIT**（`compose-shared-elements`）：保留版权声明与许可声明即可，无 NOTICE 要求
- [ ] **未声明许可证**（`canopas/compose-animations-examples`、`EasingCompose` 字段为 NOASSERTION）：
      **一律不抄代码**，只可参考效果后自行实现
- [ ] 真正引入依赖时，把库名、版本、许可证加进「关于 → 文档 → 开源许可」——
      现在那一页只覆盖字体与运行时依赖，没有这层
- [ ] 概念与模式的借鉴（如「Shared Axis / Container Transform」）属于思想，不需要署名，
      但文档里注明出处更体面

## 已发布：0.32.4 字体不随系统缩放

根因：`sp = dp × fontScale` 跟随系统放大，而卡片高度写死 dp，字号变大容器不变就被裁。
修法：固定高度容器内的字号统一走 `fixedSp(v) = (v / fontScale).sp` 反向补偿。
不做：全局禁用 fontScale（会牺牲无障碍设置）。
