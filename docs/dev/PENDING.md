# 详细方案

## 字体不随系统缩放（0.32.4，已发布）

用户反馈：系统调过字体后，卡片与小组件的文字显示不完整。

**根因**：`sp` = `dp × fontScale`，跟随系统字号设置放大；而卡片高度是写死的 dp
（资讯卡 `CARD_ROW_HEIGHT = 62.dp`、小组件由 launcher 决定格位）。字号变大、容器不变，
底部就被裁掉。这是尺寸体系不自洽，不是某个字号写大了。

**修法**：所有「固定高度容器」内的字号按 fontScale 反向补偿，让实际像素恒定。

- [ ] **[目视]** 资讯卡 `ui/news/NewsCardView.kt`：`DateStamp` 与 `DayCardRow` 的字号
      统一走一个 `fixedSp(value)` 辅助函数（`(value / fontScale).sp`），
      卡片高度、行高、间距保持不变
- [ ] **[目视]** 小组件 `widget/NextClassWidget.kt`：同样补偿。
      Glance 拿不到 `LocalDensity`，用 `LocalContext.current.resources.configuration.fontScale`
- [ ] **[目视]** 应用内其他固定高度处一并检查：`ui/settings` 的入口行、`ui/timetable` 的节次栏
- **不做**：全局禁用 fontScale（`attachBaseContext` 里改 configuration）。
  那会牺牲系统无障碍设置，影响所有文字，代价远大于收益

用户反馈：边距太粗、样式不好看、字体过度依赖系统。

每轮都是「先编再装再看」，成本远高于画一张图。

**草图 v1 已确认的要点**（见对话中的 SVG）：

- [ ] **[目视]** 去掉 1dp 描边。分层靠卡片填充色与壁纸的对比，不靠边框
- [ ] **[目视]** 圆角 20 → 22dp，内边距 8 → 14dp。当前两者比例失衡：边太窄、角太厚
- [ ] **[目视]** 顶部左侧「下一节」11sp 次要色；右侧加时间胶囊（`15:30`，白 7% 底、圆角 12dp）
- [ ] **[目视]** 分钟数 46sp、红色，占卡片高度约 40%；单位 14sp 紧贴数字下沿
- [ ] **[目视]** 课名 20sp 粗体、详情 12sp 次要色，靠字重分层，不加分隔线
- [ ] **[目视]** 列表形态同步：去边框、行高与内边距按同比例调整

**三态判定（草图已出，待实现）**：

`ScheduleService.planForToday` 已经剔除已结束的课，但它把「今天没了」的情况处理成
「顺延到明天」，所以 `isTomorrow` 不能用来看作「课程结束」以外的含义。
需要在 `loadState` 里再算一次状态：

- `ONGOING`：当前分钟数落在某节课的 `[startTime, endTime]` 区间内
- `NEXT`：`isTomorrow == false` 且不在上课中
- `FINISHED`：`isTomorrow == true`（今天的课都结束了，列表里其实是明天的课）

| 状态 | 顶部 | 中部 | 底部 |
|---|---|---|---|
| NEXT | 「下一节」+ 右侧时间胶囊 | 红色分钟数 + 「分钟后」 | 课名 + 时间教室 |
| ONGOING | 无标签，只留时间胶囊 | 红色「正在上课」 | 课名 + 时间教室 |
| FINISHED | 无 | 蓝色「课程结束」 | 不显示 |

- [ ] **[目视]** `WidgetState` 加 `mode` 枚举，`countdown()` 不再负责判断状态，
      只负责算分钟数 —— 它现在把「正在上课」混在比大小里，两个职责绞在一起
- [ ] **[目视]** 「正在上课」四个字在 82dp 内容宽内上限约 20sp（中文全角，4 字占满），
      再大必然折行。与课名 16sp 靠「加粗 + 红色」拉开层级，不靠字号
- [ ] **[目视]** 「课程结束」用蓝色 `#6FA8FF`，与红色 `#FF6B5E` 分属两个语义：
      红=紧迫，蓝=无事发生。文字在卡片内垂直居中，不留空白课程行

**列表两形态（草图已出）**：

高度是要先算的账。4×2 共 110dp，减去上下内边距 28dp 只剩 82dp；
标题行占 16dp 后剩 66dp，行高 45dp 只能放 **1.4 行** —— 之前写的「一屏 3 门」
在 110dp 高度下不成立。

- [ ] **[目视]** 4×2：行高压到 38dp，一屏 **2 行**，第三行起滚动。
      列宽：时间 46 + 色条 3 + 课名弹性 + 教室 62 + 节次 30
- [ ] **[目视]** 2×4：行高 58dp，一屏 **3 行**（220dp − 28dp 内边距 = 192dp，
      标题 20 + 3×58 = 194，刚好）。省掉节次列，教室放在课名下
- [ ] **[目视]** 两形态都不画行间分隔线，靠色条与留白区分

**参照图（墨墨记账）可学的六点**：

1. **无边框**：深色卡片直接压在壁纸上，靠明度差分层
2. **单一焦点**：一个高饱和元素（金额 / 分钟数），其余全部降饱和
3. **右上角弱化 chip**：功能信息用低对比底，不参与主体层级
4. **数字是主角**：金额字号是标题的 2.5 倍
5. **纯文字分层**：灰小字 → 白小字 → 白大字 → 彩色明细，只有四级，无装饰
6. **紧凑内边距**：14dp 左右，元素贴得近但不挤，靠字号与颜色区分而非留白

## Flutter 评估（结论：不切换）

**结论**：当前不切换。不是因为 Kotlin 更好，而是这个应用的重心不在 UI 层。

**四条成本**：

- **小组件、通知、闹钟、前台服务仍要原生**。Flutter 没有官方 AppWidget 支持，
  这些模块一行都省不掉，反而多了两层（Dart ↔ 平台通道 ↔ 原生）
- **包体**：Flutter 运行时 +10~15 MB，现在是 2.8 MB
- **启动**：Dart VM 初始化，冷启动比现在慢一档；这个应用的定位是「打开就看课表」
- **已有五个模块成型**：解析器（xlsx/docx/rtf）、Room 迁移、抓取与清洗、通知调度、
  小组件。重写等于把踩过的坑重踩一遍

**Flutter 真正的优势**：自绘 UI 一致性强、动效与手势能力强、跨平台。
这三样在「单一 Android 端 + 信息密度优先」的场景里，收益不足以覆盖成本。

**重新评估的触发条件**（任一成立则重新算）：

1. 要做 iOS —— 跨端收益首次大于成本
2. UI 需要大量自绘或复杂手势（如全屏手势课表、动画化的周视图）
3. 多人协作，需要统一技术栈降低沟通成本

**若真要做，时点选在 0.33.1 资源包外置之后**：那时数据层（校历、资讯源、入口配置）
已经移出 APK，Flutter 只重写展示层，原生保留小组件 / 通知 / 闹钟。
现在换（0.32.x）会把刚稳定的小组件与资讯页一起推倒。

## 卡片名言（候选，未排期）

结论：技术上可行，产品上需限定条件。倾向做，但只填补单条日的空白，不做全局装饰。

为什么可行：

- 数据完全本地，`assets/quotes.json` 三十来条，按 `dayOfYear % size` 取，零网络、零权限
- 落点正好是既有空白：单条日卡片下半部分空着，名言填的是空隙，不额外占位
- 成本低：一个数据类加一个 Composable，约 60 行

四条限制，缺一条就不做：

- 只用**无版权争议**的文本：古文、公版外文原著直译，或不署名的谚语。
  **不引用现代译本** —— 朱生豪译莎士比亚、傅雷译罗曼罗兰这类译文仍在版权期内
- **只在单条日出现**。两条及以上不显示，否则挤压资讯，卡片越长越显得啰嗦
- **不做每日推送与红点**。一旦主动推送，性质就从工具变成内容产品
- 提供关闭开关（`SettingsStore` 加 `keyCardQuote`），默认开启

反对意见也要一并记下：

- 课表工具的核心价值是「快」，名言会拖慢扫读
- 一年 365 天需要 365 条，实际只会写 30–50 条，用户一学期会反复看到同一句
- 有了内容属性，用户就会期待「换一句」，于是要交互、要库存，成本会滚雪球

判断：先做 30 条、只放单条日、可关。若收到「多余」的反馈就撤掉 —— 回退成本很低，
试探的代价可以接受。

## 增量更新：App 更新器（0.33.0，已发布）与资源包外置（0.34.0，已发布）

**结论：APK 层面没有「不安装」的更新。** Android 的更新模型就是「装新包覆盖旧包」，
差分包（bsdiff/bspatch）只减少下载体积，安装这一步省不掉。
真正能省掉安装的是**内容外置**。

**先澄清一点**：覆盖安装**不会丢数据**。同签名 + `versionCode` 递增即可原地升级，
Room、DataStore、课表都在。只有签名变了或卸载重装才会清空 ——
所以「更新要重装」不等于「要重新导课表」。

> **这条前提在 0.33.0–0.33.1 被违反了**：那两个版本沿用 `debug` 签名，而 debug keystore
> 是 CI runner 首次构建时按机器生成的，每次构建都不一样。结果每个版本的证书都不同，
> 新包装不上旧版本（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`），更新器从未成功过。
> 0.33.2 起改为固定密钥，密钥在仓库外的 `keystore/`，CI 通过 Secrets 传入。
> **以后不要再退回 debug 签名。**

| 方案 | 要不要装 | 省多少 | 代价 | 结论 |
|---|---|---|---|---|
| A 完整 APK 覆盖安装 | 要 | 0 | 2.1MB | 做，这是底座 |
| B 差分包 bspatch | **要** | 30~60% | patch 矩阵 + 合成失败回退 | **不做** |
| C 内容外置（远程 JSON） | **不要** | 100% | 版本号 + 校验 + 离线兜底 | **做** |

B 不做的理由：2.1MB 的包顶多省 1MB；用户可能从 0.30.2 直接跳 0.32.0，
要么存 N×(N-1)/2 个 patch，要么做链式（任一环坏整条失效），再叠上签名校验、
合成后安装失败的回退 —— 维护成本远超收益。

### 0.34.0 的落地情况

已实现（`data/pack/`）：

- `latest.json` 清单 + `<version>/<path>` 取文件；版本号 `yyyyMMddHHmm` 存 Long，只升不降
- 逐文件 sha256 校验；`minAppVersion` 挡住旧版整体跳过；内容不合格记 `failedVersion`，同版本不再重试
- 目录 `filesDir/pack/<version>/`，写完整目录后再原子改 `state.json`；
  读过一次失败就退回 `assets/`，内置那份永远能跑
- 两个下载源写死在代码里（GitHub raw → jsDelivr），先试 raw（与 App 更新同源、无缓存延迟），
  连接超时 6 秒后回退
- 入口链接单独设卡：不允许引入新域名，非 https 一律拒绝（内置里本来就是 http 的一卡通除外）
- 「调试面板 → 资源包」显示当前版本、来源、上次检查，并有手动检查按钮
- 启动后延迟 10 秒自动检查，与版本检查互不调用、日志分 `[Pack]` / `[Update]`
- 恢复出厂设置会清掉下载的包

**已接入的读取处**：`CalendarRepository`（校历）、`PortalCatalog`（入口列表）。
发布脚本：`tools/publish-pack.sh`，资源在 `packs` 分支（单独分支，避免每次发资源都触发 APK 构建）。

**0.34.1 已做**：资讯栏目与抓取规则外置（`news/sources.json`）。
栏目（id/名称/地址/来源）与规则（链接选择器、正文容器、日期与 id 正则、噪声词）都在配置里，
算法仍留在 `NewsCrawler`。两类内容在应用资源包时都会过 `PackGuards`：
资讯配置额外限制「栏目域名必须在内置集合内」，因为它能决定应用去请求谁。

**未做**：课表解析词典（`FieldExtractor` 的周次/节次/教师正则、表头词），排到 0.34.2。

为什么单独放一版：资讯抓取坏了表现为「抓不到新闻」，用户一眼能看出、也能退回内置；
而**课表解析坏了是静默的** —— 正则把「1-16周」读成「1-6周」，导进去的课表少了一半周次，
界面上完全正常。这种错没法靠看界面发现。

所以 0.34.2 的前置是**解析自检**，不是先写代码：

- [ ] 应用资源包时，用新词典解析 `assets/samples/timetable_sample*.txt`，
      与内置词典的结果逐字段比对；不一致就整包拒绝
- [ ] 自检失败要记日志并写明「哪个字段、期望什么、实际什么」，否则没法判断是词典错了还是样例变了
- [ ] 表头词只做「增补」不做「替换」：新词可以加，旧词不能被远程删掉

在这三条落地之前，课表正则不出 APK。

**一处没做到的**：PENDING 原计划「整个 pack 的 sha256 写在 APK 内置 manifest 里」。
远程包的内容事先不可能知道哈希，这条只对**随包附带**的资源包成立。
现在的完整性保证是「逐文件 sha256 + 固定 https 源」，防的是传输损坏，防不住服务端被换包 ——
后者与 APK 下载处于同一信任级别（都是 GitHub 本仓库），没有额外恶化，但也不要以为它更强。

### C 的落点：哪些内容该外置

| 资源 | 现状 | 外置价值 | 变动频率 |
|---|---|---|---|
| **资讯源与正文规则** | `NewsSource` / `NewsCrawler` 里的栏目与选择器 | **最高**：学校改版即失效，现在只能发版 | 不定期 |
| **课表解析词典** | `FieldExtractor` / `TextTimetableParser` 的表头词与正则 | **最高**：各学院导出格式不一，可随反馈持续补 | 持续 |
| **校历 + 作息模板** | `assets/calendar/nbu_calendar.json` | 高：每学年必变，「第几周」全靠它 | 1~2 次/年 |
| 开学日期推定规则 | `TermStartResolver` 的关键词与规则 | 高：校历抓不到时全靠它 | 1 次/年 |
| 入口列表 | `assets/portal/entries.json` | 高：换域名、加系统 | 不定期 |
| 服务公告 | 无（新增 `notice.json`） | 中：开学季提示、维护通知 | 不定期 |
| 许可清单 | `assets/licenses/index.json` | 低：换依赖才动 | 极低 |
| 提示文案 | 现在硬编码在 Kotlin 里 | 低：改文案仍建议发版，否则和截图/文档脱节 | — |

**必须不外部化的三类**：

- **域名白名单与安全策略** —— 根必须在内置代码里，否则远程包能把用户导到任意地址
- **用户数据** —— 课表、自定义作息、设置，这些是本机状态，不是资源
- **解析算法本身** —— 只外置「词典 / 选择器 / 关键词」，不外置代码

### 版本规则：资源独立版本，单向兼容

- [ ] 单一资源包 `pack`，版本号用 **`yyyyMMddHHmm`（如 `202610291248`）** ——
      照 MAA 的做法：**版本号本身就是时间**，精确到分钟，人一眼能看出新旧；
      与 App 的 `versionName` 完全解耦，资源发多少次都不影响 App 版本
- [ ] 为什么精确到分钟而不是只到日期：两个包在同一天发两次是常态
      （上午修入口、下午补资讯源），只到日期就会撞版本、被迫加序号；
      也不用精确到秒 —— 同一秒发两个包不现实，而 12 位已经够短
- [ ] `version` 用 **Long** 存（12 位，远小于 `Long.MAX`），比较直接比 Long，不要比字符串；
      展示时格式化回 `2026-10-29 12:48`，不要让人读 `202610291248` 这种 12 位连写
- [ ] 与 `updatedAt` / `notes` 的分工：`version` 只用于比较排序；
      `updatedAt`（ISO 8601）与 `notes`（这次改了什么）只用于展示 ——
      `updatedAt` 进「数据与诊断」，`notes` 进应用内更新日志的「资源更新」块。
      **三者不能混用**：拿 `updatedAt` 去比大小，只要服务端换时区就可能出现"版本倒退"
- [ ] pack 内每个文件带 `sha256`；**整个 pack 的 sha256 写在 APK 内置的 manifest 里**
      （包内自带的清单不算数，否则等于包自证清白）
- [ ] **只升不降**：`remote.version > local.version` 才应用，更旧的包一律拒绝
- [ ] **资源不向下兼容**：pack 声明 `minAppVersion`（对应 `versionCode`），
      当前 App 低于它就整体跳过，**不做部分应用** —— 半套新资源比不更新更糟
- [ ] **新 App 必须读得动旧资源**：schema 只增字段、不改语义、不删字段；
      要删字段就等最老的支持版本整体淘汰。`assets/` 内置包永远能跑，这是底线
- [ ] 应用失败（校验 / 解析 / 结构不符）→ 回退内置包，记 `[Pack] 回退 原因=...`，
      同一版本不再重试，避免每次启动都卡一次
- [ ] 「数据与诊断」页显示当前 pack 版本与来源（内置 / 下载），反馈时一眼能定位

### 版本检查与资源检查必须分开

三条理由，任何一条都足以让它们不能合成一个「检查更新」：

| | App 版本 | 资源包 |
|---|---|---|
| 动作 | 下载 APK → **跳系统安装器** → 用户确认 | 下载文件 → 写私有目录 → 静默生效 |
| 节奏 | 低频、手动为主（一天/一周一次） | 高频、后台自动（每次启动都可能） |
| 失败后果 | 装到一半失败，用户看得见 | 静默失败，用户只看到「资讯空了」 |
| 版本号语义 | `versionCode` 单调递增 | `yyyyMMddHHmm` 时间戳式 |

合成一个的后果很具体：用户点了「检查更新」，结果只是资源变了、App 没变，
他会以为更新坏了；或者反过来，一个 200KB 的资源包让他以为要装 2MB 的包。

- [ ] 两个检查器、两套状态：`AppUpdateChecker`（GitHub Release 的 `manifest.json`）/
      `ResourcePackChecker`（pack 的 `latest.json`），互不调用
- [ ] 两处 UI：版本 →「关于」页显式「检查更新」+ 更新说明 + 是否安装由用户决定；
      资源 → 只出现在「数据与诊断」里（当前 pack 版本 / 来源 / 上次检查时间），**不弹窗**
- [ ] 两条日志：`[Update] ...` 与 `[Pack] ...`，不要混写成一条「检查更新」，
      否则出问题时看不出是哪一层
- [ ] 两个节奏：版本检查**每 24 小时最多一次**且只在用户进入「关于」时触发；
      资源检查在启动后延迟 8~10 秒（避开首屏合成与新闻抓取），成功即应用
- [ ] **失败互不影响**：资源检查挂了不能让版本检查沉默，反之亦然
- [ ] 资源被 `minAppVersion` 挡住时，**只记日志、不串联到版本 UI**。
      一旦写成「有新版本可解锁新资源」，两个状态机就被绑在一起，
      以后每次改资源都要考虑怎么提示升级 App
- [ ] **共享的只有基础设施**：HTTP 客户端、ETag 缓存、镜像 fallback、sha256 校验、
      版本比较工具。共享工具，不共享状态机 —— 这是「分开做」的边界

### 参考 MAA 的资源更新（实地看过其实现，10-29）

MAA 能"不重装就更新"的根本原因：**它的资源是 `resource/` 目录，不是安装包**，
更新就是覆盖文件。Android 的 APK 是签名整体，这条在客户端上照搬不了；
但它的**分发机制**几乎可以整套搬给「内容外置」。

可以直接抄的六条：

- [ ] `version.json` 里用 **`last_updated` 时间戳**当版本号，不搞语义版本 ——
      MAA 就是这么做的（`resource/version.json`），比较大小、生成、迁移都最省事
- [ ] **拒绝比当前更旧的包**。MAA 明说"不会导入比当前更旧的包"。
      我们原来只想到 `minAppVersion`（防新包发旧端），缺的反向保护是"防旧包覆盖新数据"
- [ ] **ETag / If-None-Match 条件请求**（MAA 的 `Helper/ETagCache.cs`）：
      版本没变时服务端回 304 无 body，比每次都下 `version.json` 更省。jsDelivr 支持
- [ ] **镜像列表逐个 fallback**：MAA 把 GitHub Release 链接和镜像一起塞进候选地址。
      我们对应 GitHub raw → jsDelivr → 内置，三级
- [ ] **增量包只合并不删除**：MAA 的资源包是"增量内容，不删原有文件"。
      所以远程包必须按文件合并，绝不能"用远程目录整体替换本地目录"
- [ ] **全量包兜底**：MAA 的 GitHub 路径就是下全量 zip 解压合并；
      增量包损坏或校验失败时，要能退回全量

明确不抄的两条：

- ❌ **客户端文件级 OTA**：MAA 是 Windows/Linux 便携程序，覆盖 exe/dll 即可；
      Android 只能整包签名安装，没有对应物
- ❌ **MirrorChyan CDK 付费 CDN**：MAA 的增量通道靠这个，我们不能引入付费依赖

一个参考数值：MAA 的资源有几十 MB，文件级增量收益显著；我们的 `assets/` 只有 64KB，
**逐文件增量的流量收益可以忽略**，抄它的价值在"机制正确"（版本、校验、回退、镜像），
不在"省流量"。

### 现成模板：MaaMeow 的「双层更新」

仓库 `Aliothmoon/MAA-Meow`。**本体与资源是两条更新通道**：

| 层 | 怎么更新 | 要装吗 |
|---|---|---|
| APP 本体（含 MaaCore）| GitHub Release 下 APK 覆盖安装 | **要**（arm64 177MB / universal 199MB） |
| 资源（`resource/`）| 应用内直接下载资源包到应用私有目录 | **不要** |

这一点很重要 —— 我上一版据 Release 里「内置 MaaCore 升级至 v6.20.0」推断它"没有独立资源更新"，
**是错的**：core 跟包走，资源不跟包走。改一条资源不需要重下 177MB。

它的资源更新之所以能免安装，只有一个原因：**资源落在 `filesDir`，不在 APK 里**。
这跟桌面版 MAA 是同一个模型，只是换了个落点。

对我们最直接的四条启发：

- [ ] **双层更新是 Android 上唯一能"免安装"的形态**：体走 APK，内容走文件。
      这比"减少安装包体积"重要得多 —— 少装一次，就少过一次「安装未知应用」那道坎
- [ ] **APK 内置一份 + 允许更高版本覆盖**：MaaMeow 的包里带一份资源，
      所以首次启动不联网也能用。我们的 `assets/` 正好就是这个角色，不用改结构
- [ ] **资源包格式与端无关**：桌面 MAA 和 MaaMeow 吃同一套 zip + `version.json`。
      我们的远程包也应如此，将来做桌面端/网页端可直接复用
- [ ] **免安装顺带免权限**：APK 更新在 MIUI / ColorOS 上要用户单独开「安装未知应用」，
      资源更新则只是写自己目录 —— 这是两条通道体验差的根源

**我们比它多一层风险，必须额外处理**：MaaMeow 的资源是游戏数据，改坏了只是功能异常；
我们的 `assets/portal/entries.json` 是**跳转 URL 列表**。远程包一旦被篡改，
可以把用户导到钓鱼页面。所以内容外置必须比 MAA 更严：

- [ ] **下载源写死在 APK 里**（GitHub raw → jsDelivr 两条），不接受远程包自己指定新源
- [ ] 远程包整体 **sha256 必须在 APK 内置的 manifest 里**（而不是包内自带的清单），
      否则"包自证清白"没有意义
- [ ] 只接受 https；`entries.json` 里出现 http 链接一律拒绝该条
- [ ] 远程包不能引入新的 host（域名白名单仍以内置清单为准）

### A 的落点（应用内更新器，0.33.0 已发布）

- [x] `manifest.json` 放 GitHub Release：`{versionCode, versionName, apkUrl, sha256, notes}`
- **坑**：不能用 `releases/latest/download/manifest.json` —— 该端点只返回非 prerelease，
  本项目全是预发布，会一直取不到。要用 `releases?per_page=1` 列最新一次发布，
  再从资产的 `browser_download_url` 取清单（0.33.1 修正）

- [ ] 需要 `REQUEST_INSTALL_PACKAGES`；MIUI / ColorOS 还要用户开「安装未知应用」，
      **做不到真正静默**，文案必须写清
- [ ] sha256 校验通过才交给安装器；`PackageInstaller` 失败回退 `ACTION_VIEW` 传统安装
- [ ] `versionCode` 严格递增，否则覆盖安装会被系统拒绝

# 验收方式：能用导出日志判的，就不走 ADB

现状：验收基本靠「ADB 连机 → 手工点 → 看屏幕」，设备一掉线整轮验证就停摆（0.30.3 就是这样）。
但界面上真正需要眼睛的只有**间距、颜色、对齐**；剩下的「点完发生了什么」「状态变没变」
都能由应用自己写进工作日志 —— 用户导出、贴过来，我读日志判定，零连接成本。

## A. `AppLog` 加结构化事件

`util/AppLog.kt` 只有 `log(tag, message)` 自由文本，靠拼字符串，不好 grep。

- [ ] 新增 `AppLog.event(tag: String, name: String, vararg fields: Pair<String, Any?>)`，
      输出 `[tag] name key=value key=value`；单条仍受 500 字符上限约束
- [ ] 加 `AppLog.assert(tag: String, name: String, ok: Boolean, detail: String)`：
      `ok=false` 时以 `[Assert]` 前缀落一条，和普通记录区分开

## B. 关键交互打点（每条都替代一次 ADB 手点）

- [ ] 周次跳转（`TimetableScreen`）：请求时打
      `[Nav] 请求 目标=8 来源=本周|箭头 基准=1 距离=7 方式=瞬移|动画`，
      落位时打 `[Nav] 落位 8 耗时=63ms` —— 这次的「本周只生效一次」用这两行就能抓到
- [ ] 提醒开关（`ReminderCard`）：`[Set] reminder on|off 来源=卡片`、
      `[Set] live on|off`、渠道状态每次变化打一条（现在只在页面打开时回显，不进日志）
- [ ] 后台运行跳转（`BackgroundRunCard`）：`[Sys] 跳转 自启动|电池策略 成功|回落`
- [ ] 入口页（`PortalScreen`）：`[Portal] 点击 id=C3 结果=浏览器|复制|校历`，
      只记 id 与结果，**不记课程名、不记 URL**
- [ ] 页面进出（`AppRoot`）：`[UI] 进入 设置/提醒` / `[UI] 返回 课表`
- [ ] 主题（`AppearanceScreen`）：`[Set] seed=blue dark=follow backdrop=grad1`

## C. 不变量自检：让日志自己报告失败

- [ ] `[Nav]` 请求后 800ms 内无落位 → `[Assert] nav.stuck 目标=8`
- [ ] 落位页 ≠ 目标页 → `[Assert] nav.mismatch 期望=8 实际=7`
- [ ] 验收清单直接写「**日志里不得出现任何 `[Assert]`**」，一条都不用人工盯

## D. 导出时带「本次运行摘要」

`AppLog.dump()` 现在是纯流水，读的人要从 27 行里数。在正文前加 8～10 行汇总：

- 运行时长、启动次数、切周次数（其中瞬移 N 次）、
  `[Assert]` 计数（0 才正常）、提醒重排次数、`[Perf]` 最差一次掉帧

## E. 体量：加打点后必须先做合并

500 条上限不变，但交互密集时会顶满，真正异常会被挤掉。

- [ ] `[Nav]` / `[UI]` 这类高频事件做同秒合并：同 tag 同 name 只留最后一条，追加 `×N`
- [ ] 打点**零成本**：`AppLog.log` 是 synchronized + 字符串拼接，绝不能进滚动/每帧路径。
      `FrameStats` 继续保持独立通道

## F. 注意事项

- 日志会被用户导出分享 → `[Portal]` 只记入口 id、`[Nav]` 只记周次数字，
  任何课程名/教师/学号都不进日志（`AppLog` 已有脱敏规则，新事件要遵守同一条）
- `[目视]` 项尽量压到「一张截图能判」；「卡不卡」这种不写进清单，改看 `[Perf]` 的掉帧数
